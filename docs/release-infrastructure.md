# Immutable publication and recovery

Git is the authoritative source for records, stable IDs, relationships, coverage inputs, snapshots, rights and provenance. Storage is a reproducible publication derivative, not a second editorial database. No accounting review status changes with this infrastructure work.

## Ownership and layout

- Current structured data is compiled to immutable, content-addressed compressed static assets. Executable modules load these assets when the application is first requested. Agent passage generation is deferred to the selected records instead of retaining passages for the whole corpus. Current records and indexes remain in isolate memory after initialization.
- D1 is not introduced. The current 1,328-record corpus has no public writes or transactional editorial workflow, and retaining its existing retrieval implementation avoids changing search semantics. This choice must be revisited if measured current-data/index memory exceeds the runtime envelope.
- R2 stores content-addressed compressed chunks of historical releases, complete coverage history, portable downloads and the complete source export. Existing logical paths, file bytes and SHA-256 contracts are preserved. Content-defined boundaries allow unchanged archive tails to deduplicate even when earlier source entries change size.
- The application embeds only the small immutable file manifest. It streams bounded chunks with backpressure. HEAD and conditional requests use build-time metadata, avoiding reads of download bodies. Full history is never imported into executable modules; only the summary used by the coverage page is bundled.
- Local `dist/client/downloads` and `dist/client/releases` retain logical output for verification. They are excluded from deployment staging, together with upload objects and internal development bundles. They are not deployment inputs.

## Publication sequence

1. Prepare/finalize content through the [edition workflow](edition-preparation.md), review and commit it, and obtain complete required PR and successful main verification. Use the [authoritative release artifact](release-artifact.md) from that main run. Application, assets, metadata, downloads and storage objects are produced by that one verified build.
2. Run the required production-output browser checks. Capture their actual source, input and build identities. An unchanged output directory or old receipt is not verification. No later publication gate silently rebuilds the app or reruns the complete suite.
3. Read the existing Site using native `get_site`, version and deployment status tools. Preserve the public audience, unrelated environment values and the prior saved version. Record the selected project, origin, live deployment, saved source ancestry and environment revision outside source inputs. Open the Sites checkout with the installed `sites-hosting` workflow before modifying it.
4. Configure a temporary `RELEASE_IMPORT_TOKEN` with native Sites environment tools, preserving all unrelated values; apply the environment through the supported deployment operation. Keep the token in memory and hidden stdin, never in shell arguments, logs, files or artifacts. The public corpus stays read-only; the existing authenticated import endpoint exposes no activation or deletion operation.
5. Run `node scripts/stage-release.mjs RUN ATTEMPT FULL_MAIN_SHA PACKAGE_DIRECTORY ARTIFACT_ZIP FRESH_STAGE HTTPS_ORIGIN PROJECT_ID`, providing the token only on stdin. The caller must first verify that the native Site's origin and project match these arguments. Staging authenticates live GitHub run/job/artifact/main state, hashes the cached ZIP against the authenticated platform digest, binds the extracted package manifest to that ZIP, and validates all package/storage bytes. It imports immutable objects with read-back before retries, revalidates the full manifest seal, checks current GitHub identity again, and copies the exact application members. It executes no downloaded scripts and performs no app build. A standalone `import-release.mjs HTTPS_ORIGIN STORAGE_DIRECTORY` accepts the same stdin credential, but cannot stage or activate anything.
6. Copy the verified application stage into the opened Sites source checkout, preserving its source ancestry and unrelated files. Account explicitly for each changed or removed generated deployment file; verify staged member hashes before and after the handoff. Run the installed Sites workflow with `commands: []` and an archive path. The Sites wrapper commit identifies the packaging checkout, while the GitHub revision remains embedded in the unchanged verified application. Save the returned wrapper commit and unchanged archive through native `save_site_version`, then deploy that exact saved version with the existing audience. Record both identities and the declared packaging transformation.
7. Immediately before deployment, reread native Site/version/deployment state and current main. Stop if another release advanced the recorded state. Use one local release owner/lock. Reconcile uncertain save/deploy responses by native read-back before retrying; never infer success from a local JSON receipt. The installed deploy tool has no expected-current-deployment parameter, so it cannot provide an atomic compare-and-swap against another external deployer between read and activation. Preserve this provider limitation in the review/operational record.
8. Observe terminal native deployment success, then verify live graph/reading/search/filter journeys, research content, API/corpus/index identity, runtime assets, security headers and download integrity against the intended package. A saved version or green local check is not publication evidence.
9. Remove the temporary import secret through native environment tools, preserve unrelated values, and redeploy the same saved version if needed to apply the final environment revision. Confirm terminal success, native environment state and live behavior after cleanup. Retain prior saved versions, all immutable storage objects, and failed-attempt evidence.

The `.stage.json` sidecar is a compact record of inputs, hashes, import measurements and copied members, not future deployment authority. Resume from the last valid stage by rereading remote state. Cached-artifact authentication avoids retransferring an unchanged ZIP but still hashes it and validates the extracted bytes. Missing/corrupt caches or expired/missing artifacts require the recovery described in `release-artifact.md`. Stage, native save/deploy and final cleanup results belong in the operational checkpoint outside the source inventory.

## Failure and rollback

A failed upload cannot change the live manifest: there is no mutable current-data pointer. Partial content-addressed objects remain inert and can be reused by retry. Staging does not accept import receipts as authority; it authenticates the artifact and repeats the idempotent remote seal checks. A release refuses to serve from an unsealed R2 manifest. A missing object returns unavailable or terminates an incomplete stream; it never falls back to bytes from another edition. Retain all older objects and saved application versions. An authorized rollback uses the prior saved version and same audience, only after reconciling current deployment state; a rollback is not an automatic retry. Do not delete storage as part of routine release cleanup.

The initial transition deploy retains the previously live corpus while adding the authenticated import endpoint and R2 binding. Only after import validation does the new application become eligible for activation.

## Qualification and constraints

Cloudflare's [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) document 128 MB isolate memory, a 64 MiB Worker module limit, 25 MiB per static asset and a one-second startup limit. These are underlying platform limits, not proof of this Sites project's complete effective configuration. The old 256 MiB Sites expanded-archive limit appears only in earlier failure evidence. This repair uses the independently successful 237,793,280-byte transition archive as a conservative known-working packaging boundary, without claiming it is the current platform maximum.

`npm run check` includes deployment qualification. It rejects full snapshot/release imports, oversized Worker/static artifacts, loss of source/export record parity and package growth beyond the known-working boundary. Storage tests reconstruct every download, exercise missing objects, authenticated imports, incomplete seals, conditional reads and content-defined deduplication. Source-export tests verify complete source membership and deterministic bytes. Qualification is necessary but must be followed by native deployment success and live checks.

Remaining scaling tradeoff: current data and search indexes still reside in each initialized isolate. Historical growth no longer expands executable code or the application upload, but does consume storage. Source archive creation remains an offline operation proportional to the retained source history. No new paid service or different hosting audience is configured.

CI previously stopped at its ten-minute job limit during source-export verification and retained an 872 MB artifact containing duplicate generated history. Its bounded job window is now twenty minutes. CI retains the complete revision source ZIP, application runtime/data assets and qualification manifests for diagnostics. Successful main runs additionally retain the complete authoritative application/storage package, including required immutable objects, for 14 days. This increases transfer and retained bytes; report those costs separately from build/test improvements. The first package measured 370,686,976 bytes plus a 189,643,264-byte diagnostic artifact.
